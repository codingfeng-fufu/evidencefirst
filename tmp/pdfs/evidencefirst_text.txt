      Abstract. Fixed-context Web question answering needs more than a
      posthoc answer trace: operators need to know, before generation, whether
      the graph evidence is ready for the reader and what action to take
      when it is not. EvidenceFirst introduces a pre-reader evidence-state
      contract for GraphRAG. A deterministic checker records each question
      as checked path, repaired path, residual gap, or passage fallback, and this
      typed state controls localized repair, fallback, answer selection, and later
      replay. Across saved HotpotQA-1000 and 2WikiMultiHopQA-500 artifacts,
      EvidenceFirst attaches this contract to competitive answer outputs:
      HotpotQA reaches 55.0% EM / 64.8% F1 end to end and 56.2% EM /
      65.6% F1 under deterministic selector sensitivity; these point estimates
      are above HopRAG strict, while full-set paired intervals cross zero. The
      context-rich 2Wiki reader-full artifact reaches 69.0% EM / 75.8% F1 and
      a local-context stress row quantifies the boundary at 50.4% EM / 59.5%
      F1. The same saved states create recomputable audit queues without
      new LLM calls: the top-20% audit-risk queues contain 67.0% and 40.0%
      answer errors, and a reviewer-facing verifier checks 38 required artifacts,
      42 integrity fingerprints, and 17,500 independently rescored rows.

1   Introduction

Knowledge-intensive Web applications require answers that are both grounded and
inspectable. Consider an enterprise or search-style Web QA service that answers
from fixed retrieved pages and an entity-relation graph: when an answer enters an
audit queue, the operator needs to know whether the graph actually connected
the required evidence entities, whether the system repaired a missing bridge,
or whether the reader answered from residual passage context. RAG grounds
language-model answers in retrieved text [6], while KG-RAG and GraphRAG
systems add entity-relation structure over retrieved corpora [2–4]. This structure
is valuable because a correct multi-hop answer is often the endpoint of a connected
path through Web evidence, not merely the most likely string under the language
model. For Web information systems, reliability is therefore an evidence-state
problem as well as an answer-generation problem. In a concrete audit workflow,
2      Anonymous

a Web QA platform can take an answer flagged as a residual gap, inspect the
saved record to see that a bridge entity was missing before generation, route the
case to graph repair rather than reader debugging, and replay the same state
later without another LLM call. Without a pre-reader state contract, the same
operator only sees a retrieved-passage trace and a final answer, which is too late
to identify where the evidence path failed.
     The central reliability problem in fixed-context Web-style GraphRAG is the
state of the candidate evidence path. A system can retrieve relevant triples while
still missing the bridge edge that makes the answer derivable. It can retrieve both
endpoint entities but leave them in separate connected components. It can also
retrieve a plausible graph neighborhood that lacks the actual candidate support
chain. In all of these cases, a retrieve-then-generate pipeline may still produce a
fluent answer, but the system has already lost the opportunity to explain whether
the failure came from retrieval, graph construction, evidence connectivity, or
generation.
     EvidenceFirst addresses this problem by moving structural evidence-state
checking before generation. Instead of treating the generated answer string as
the first object to inspect, EvidenceFirst checks whether the constructed
evidence graph contains a structurally connected candidate chain for the question.
When the graph is incomplete under this structural criterion, the checker emits a
diagnostic such as missing entity, disconnected pair, bridge gap, short chain, or
empty evidence. The diagnostic is executable state rather than a posthoc tag:
it determines whether the system repairs the graph, falls back to passages, or
routes the case for later audit before the reader output is finalized.
     This design changes the role of a Web knowledge graph from passive context
to a control surface. EvidenceFirst first builds or loads the question graph,
then uses the graph state to decide whether the reader should receive a checked
candidate path, a repaired path, or passage fallback with an explicit diagnostic
record. For example, a standard trace can show that a passage was retrieved
for a father-in-law question; EvidenceFirst additionally records whether the
spouse-to-parent bridge was present before generation, whether a bridge repair
was attempted, and whether the final answer came from a residual graph state.
The output therefore supports two goals at once: answer generation and an
evidence-state record for why a Web query succeeded or failed. In a deployed
Web information system, this record can route residual-gap answers into an audit
queue, replay compliance cases without fresh LLM calls, and populate failure
dashboards that distinguish retrieval, graph construction, repair, and reader
errors over the same fixed retrieved corpus. The concrete system change is that
answer logs become typed review queues: checked-path failures go to reader or
selection inspection, residual-gap cases go to graph repair, and fallback cases go
to retrieval/context review.

tached to competitive answer artifacts and whether it creates useful review
queues. On HotpotQA-1000, EvidenceFirst reaches 55.0% EM / 64.8% F1 end
to end and 56.2% EM / 65.6% F1 under deterministic selector sensitivity, with

 – We define a pre-reader evidence-state contract for GraphRAG: every answer is

2    Related Work

RAG, GraphRAG, and multi-hop retrieval. RAG conditions a language model
on retrieved evidence [6], while GraphRAG systems organize retrieved infor-
mation into entity, relation, or community structures [2–4]. IRCoT interleaves
retrieval with chain-of-thought reasoning [10], A-RAG uses an agentic retrieval
trajectory [1], and HopRAG performs logic-aware graph retrieval and pruning [8].
These systems improve evidence acquisition or reasoning depth; EvidenceFirst
4       Anonymous

complements them by recording, before reader generation, whether the final
evidence graph exposes a checked candidate path or a concrete graph gap.

Verification and auditability. S2G-RAG judges whether evidence memory is suffi-
cient and emits text gap items [7], while RAGChecker defines diagnostic metrics for
retrieval and generation modules [9]. EvidenceFirst narrows the claim to a dif-
ferent object of control: a deterministic per-question graph state whose path/gap
label is stored before the reader is called, affects repair/fallback/selection, and
can be recomputed from saved artifacts. This matches the mechanism boundary
in Table 1 and positions EvidenceFirst as operational Web QA observability
rather than semantic proof checking.


3     Method

3.1   Problem Setting and Evidence Representation

Given a question q and candidate passages P = {pi }, EvidenceFirst first
constructs or loads a per-question evidence graph G = (V, E) whose nodes are
entities or evidence units and whose edges are extracted relations, support links, or
passage-level associations. The goal is to output a short answer a and a diagnostic
record D that explains the state of the graph evidence. Unlike a standard reader
that consumes passages directly, EvidenceFirst first asks whether G contains a
connected candidate chain for multi-hop answering.
    Candidate passages can come from search results, Wikipedia-style pages,
entity descriptions, or other linked Web documents. EvidenceFirst builds a
question-level KG from this evidence before answer generation and uses that
graph as the object of structural checking, keeping the check tied to the evidence
actually visible to the reader.
    The evidence chain is a connected support structure linking question entities
to answer-bearing evidence. Bridge questions require an intermediate entity or
relation; comparison questions require compared attributes or entities before
the reader decides the answer. This structural view is weaker than oracle proof
checking: it uses no gold annotations at test time, but exposes whether the
retrieved graph is connected enough to justify a reader attempt.
    Operationally, EvidenceFirst records a structural path-state contract before
generation. For each question, the graph state passed to the reader must be
recorded as one of four states: a checked structurally connected candidate path
found in the retrieved evidence graph, a repaired path after localized graph
expansion, a residual graph gap after unsuccessful repair, or a passage-fallback
state when usable graph evidence is absent. The diagnostic record D stores
path-checked status, path length, gap type, missing-entity and disconnected-pair
counts, repair and fallback step tags, and the final answer-selection flag. This
contract is the method’s main difference from using a graph merely as retrieved
context: generation is conditioned not only on evidence content, but also on the
recorded state of that evidence.
                              EvidenceFirst Structural Evidence Diagnostics            5

     The structural checker uses deterministic graph operations after KG construc-
tion. It extracts question entities with named-entity and proper-noun fallbacks,
filters generic terms such as “film” or “country”, normalizes strings by lowercasing
and punctuation/article removal, and maps entities to graph nodes by exact,
substring, and token-overlap matching with threshold 0.85. Candidate answer
nodes are all non-question graph nodes, then filtered by a coarse answer type
inferred from the question surface form (e.g., person, location, date, yes/no, or
comparison). To avoid accepting a spurious one-edge neighbor as a multi-hop
answer, non-yes/no questions require at least a two-edge support path, while
yes/no questions require at least one support edge. Missing-entity diagnostics
take priority, disconnected and bridge gaps are then localized from component
structure, and disconnected repair processes at most five endpoint pairs. These
rules are fixed before evaluation and are not fitted to gold answers or gold support
facts.
     The contract has three invariants that distinguish it from passive logging.
First, the state is written before the reader call, so it records the evidence
condition that controlled generation rather than a later explanation of the answer.
Second, each state has a control action: checked paths go to the reader, gap states
trigger localized repair and recheck, and residual or empty states remain attached
when the reader falls back to passages. Third, the saved fields are deterministic
functions of the graph, repair log, and selector decision, so reviewers can replay
the same state transitions without new generation.

3.2   Evidence-First Inference
EvidenceFirst performs inference in six stages, as shown in Figure 1. It first
builds or loads a per-question KG from candidate passages, retrieves triples and
local passages for the question, constructs a compact evidence subgraph, checks
candidate-path connectivity, repairs localized gaps when possible, and finally
generates a concise answer from a recorded checked-path, repaired, or fallback
evidence state. If KG retrieval returns no usable triples, EvidenceFirst records
6      Anonymous

an empty-evidence state and answers from local passages rather than silently
treating the graph as complete. Operationally, the diagnostic record is initialized
before retrieval, updated after the first structural check, updated again after
repair and recheck, and finally passed to answer selection and canonicalization.
If the repaired graph is still incomplete, the reader receives the available triples
and local passages while the residual incomplete state is retained in the record.

3.3   Path-State Checking and Diagnostic Repair
The structural checker emits structured diagnostic states rather than a single
scalar confidence score. It first checks whether any mapped question entity and any
candidate answer node are connected in the evidence subgraph. If a path exists,
EvidenceFirst extracts the shortest path as the evidence chain passed to the
reader. A path shorter than the question-type minimum is labeled as a short chain
rather than accepted as complete. If no adequate path exists, EvidenceFirst
records the concrete failure state. A missing entity means that an entity required
by the question is absent from the evidence graph. A disconnected pair means
that relevant endpoint entities are present but lie in separate components. A
bridge gap means that a partial path reaches one side of the answer entity but
lacks the relation needed to connect the reasoning chain. A short chain means
that a connection exists but is too shallow for the inferred question type. Empty
evidence means that KG retrieval returned no usable support and the reader
must fall back to passages.
    Representative saved 2Wiki records show both intended and failure cases: a
correct answer can still carry a missing-entity graph label, and a structurally
connected candidate path can still mismatch a posthoc gold-chain proxy. These
cases motivate our terminology: labels are audit/control states over the saved
graph, not semantic correctness certificates.
    Diagnostic repair is localized to the reported gap. For missing entities, Evi-
denceFirst extracts triples about the missing entity from the retrieved passages
and adds them to the evidence graph. For disconnected pairs, EvidenceFirst
processes at most five entity pairs and extracts bridging triples from the same
passage context. After each repair stage, the structural checker is run again
and the new chain length, gap type, and repair statistics are appended to D.
When the graph remains incomplete, the reader still receives the available triples
together with local passages, while D records the residual gap. This design avoids
presenting a repaired answer as if the graph had been complete from the start.
Repair uses only the candidate passage and graph context available to the system;
it does not use gold answers or gold support facts at test time.

3.4   Grounded Reading, Selection, and Canonicalization
The answer reader receives three kinds of context: the current evidence triples,
local passages associated with the evidence graph, and the diagnostic record. The
reader is instructed to produce a concise answer rather than a long explanation.
A final selection step decides whether to use the evidence-grounded postprocessed
                           EvidenceFirst Structural Evidence Diagnostics         7

answer, and a lightweight canonicalizer normalizes title casing, entity aliases,
yes/no outputs, and short answer forms when supported by the available context.
    This stage is intentionally downstream of structural path-state checking.
Reader context can compensate for imperfect graph evidence, but it cannot
erase the diagnostic record. As a result, EvidenceFirst can distinguish cases
where the graph was structurally complete but the reader failed from cases where
generation was attempted after repair or fallback. Local passage context is enabled
in the main EvidenceFirst setting and disabled only in the reader-context
ablation, so the ablation isolates how much answer realization depends on text
grounding beyond graph triples.
    The selector is conservative. It accepts the refined answer when the original
answer is malformed, when the refined answer is normalization-equivalent to the
original answer, when the refined answer is a shorter supported form, or when
it repairs a question-type mismatch such as a yes/no placeholder for an entity
question. Otherwise, the KG-grounded answer is preserved. The diagnostic record
therefore includes not only graph states, but also whether the final answer was
selected from the refined evidence-grounded path.


4   Experimental Setup

Datasets. We evaluate on two multi-hop QA settings. HotpotQA-1000 is a
1000-question distractor-style evaluation set with repaired contexts from the
HotpotQA validation split [11]. 2WikiMultiHopQA-500 is a 500-question sample
from 2WikiMultiHopQA [5]; each example contains natural-language passages
and Wikidata-derived evidence triples, entity ids, evidence ids, and answer
ids. The 2Wiki sample contains 5000 question-context pairs and 3346 unique
passage bodies for graph-based baselines. During inference, EvidenceFirst uses
the question, candidate passages, and constructed graph fields only; support
annotations, evidence ids, answer ids, and gold answers are loaded only after
prediction for offline diagnostics.
    Both benchmarks combine Web-style text with linked entities and require
multi-hop evidence composition; 2Wiki additionally exposes Wikidata-derived
support identifiers for offline diagnostics. They instantiate a fixed-context Web
QA setting rather than live Web search, so the experiments test evidence-state
control over available passages and graph evidence, not crawling, freshness, or
changing page content.

Baselines. On HotpotQA-1000, we compare with Naive RAG, IRCoT [10],
A-RAG [1], LightRAG [3], MS GraphRAG [2], and HopRAG strict [8]. On
2WikiMultiHopQA-500, the completed baselines are Naive RAG, IRCoT, A-
RAG, LightRAG, and HopRAG strict. Main tables include only completed
full-sample artifacts; the 2Wiki HopRAG strict row is a completed 500-example
saved artifact with independent strict rescoring, not a context-budget-matched re-
run. Unavailable baseline rows are deferred rather than approximated or replaced
by leaderboard numbers. For HotpotQA, the official HopRAG comparator is

Metrics and reporting boundary. We use exact match (EM) and token F1 with
standard QA normalization: lowercasing, article removal, punctuation removal,
and whitespace collapse. HotpotQA reports both the end-to-end saved run and a
deterministic selector sensitivity row over saved artifacts with no fresh LLM calls;
the selector changes 21 predictions and 12 EM labels. Pairwise claims use shared
question IDs with bootstrap CIs and exact McNemar tests; intervals crossing
zero are descriptive, and the bridge result is an unadjusted exploratory subgroup
result. Controlled ablations use explicit switches and are separated from historical
development attempts.

Implementation settings. The reported runs use the repository’s OpenAI-style
backend with qwen-plus on a DashScope-compatible endpoint unless a run
script explicitly overrides it. Answering and repair calls use temperature 0;
KG construction artifacts are cached and loaded for the reported evaluations.
The main pipeline uses max-iter 3, local passage top-k = 5, and at most five
disconnected endpoint pairs per repair pass. The deterministic selector and 2Wiki
canonicalizer make no LLM calls. Verifier thresholds and ablation switches are
fixed before evaluation. Per-example JSONL artifacts record cache status, usage,
ablation flags, path-state status, gap labels, repair/fallback steps, and answer-
selection decisions, so audit summaries can be recomputed without new LLM
calls.

Artifacts and reproducibility boundary. Every reported result is computed from
saved full-sample artifacts rather than literature leaderboard numbers. The
reviewer-facing no-LLM verifier checks the required bundle with pinned SHA256,

5     Results
5.1      Audit and Replay Utility
The first result is that EvidenceFirst turns saved GraphRAG outputs into re-
computable operational strata. The no-LLM verifier replays the artifact boundary
without fresh generation, checks source-field hygiene for 2Wiki inference arti-
facts, and independently rescores all saved prediction/gold rows before trusting
reported EM/F1 values. This replayability is the systems contribution: a reviewer
or operator can recompute which answers came from checked paths, repaired
paths, residual gaps, or fallback states, and can prioritize audit queues using the
same records rather than rerunning the model.
    The resulting queues are imperfect but useful. The composite audit-risk
signal combines answer-selection and graph-state signals; it concentrates answer
errors in the top-20% review budget (67.0% error rate on HotpotQA and 40.0%
on 2Wiki). Graph-only signals are weaker as global rankers (Table 7), but the
operational question is narrower: given an answer-selection queue, does graph
state add a repair cause code? Table 3 shows two positive conditional contrasts.
Thus answer selection supplies risk, while pre-reader graph state supplies the
route: graph repair, reader inspection, or retrieval/context review.

5.3   Operational Removals

Table 6 reports four operational removals on both datasets. Two switches are
intentionally compound: disabling structural checking also disables gap-driven
repair, and disabling reader context also disables passage-based answer refine-
ment. The largest answer-quality drop comes from removing reader-context and
refinement, which reduces HotpotQA EM from 0.5620 to 0.2360 and 2Wiki EM
from 0.6900 to 0.1840. This result shows that graph triples alone do not provide
enough surface evidence for robust answer realization. Removing graph repair
reduces 2Wiki EM by 4.0 points and HotpotQA EM by 0.8 points. Removing
answer refinement hurts HotpotQA but increases 2Wiki F1, showing that exact
canonicalization and partial-token overlap can pull in different directions.
    The checker ablation should not be read as an EM/F1 claim for graph structure.
The chain-check+repair-off row has mixed answer-level effects because the reader
can still answer from unchecked context, and it slightly improves HotpotQA
point estimates. Its cost is operational: the system no longer knows whether the
reader saw a checked path, a repaired path, a residual graph gap, or fallback
evidence, and no longer has the typed state needed to route graph repair versus
reader inspection. Thus chain checking is evaluated as the control mechanism
that creates repair and routing states, not as a standalone answer-quality booster.
Operational removals show which capabilities are logged or available under the
saved pipeline, not isolated causal gains for every component.

5.4   Audit Signals and Failure Analysis

The saved audit records expose structural states before answer scoring. On Hot-
potQA, 56.8% of examples end with a checked candidate path, repair is attempted
on 63.7%, and 43.49% of attempted repairs end with a structurally connected
recheck; on 2Wiki, the corresponding rates are 47.8%, 60.0%, and 22.0%. These
are structural recheck-complete rates rather than gold path precision. Internal
label-consistency checks over saved fields show that missing-entity, disconnected,
and short-chain labels satisfy their structural invariants on both datasets; the
HotpotQA checked-path label is 98.44% consistent because nine incomplete rows
carry an empty final gap label. Thus, the method records whether an answer

came from checked-path, repaired, or residual incomplete evidence, but it does
not claim that a structural label proves a gold semantic chain.

versus 0.5811 EM on 2Wiki. Table 7 therefore separates triage signals and reports

Thus checked/repaired states should be read as operational evidence states, not

    The structural audit states are selective but not semantic correctness certifi-
cates. Checked-path cases reach 70.29% EM and 76.81% F1, while disconnected-
gap cases fall to 45.45% EM and 53.51% F1 and short-chain cases fall to 63.64%

the gold-chain audit shows low relation recall. A gold-derived proxy audit is also
mixed: the missing-entity label has 0.6866 precision for missing gold entities, but
disconnected and short-chain labels have low proxy recall. The safe interpretation
is therefore that the states expose useful structural strata for auditing and repair,
not that they precisely identify every missing gold fact.
    To make the gap-label question inspectable, we additionally run two offline 100-
example 2Wiki audits. The first uses saved gold-chain and reader-support metrics
after prediction and inspects each row from strict gold-chain, reader-support, and
conservative meta-review perspectives. These deterministic perspectives identify
missing-entity as the most reliable state, with a 0.7429 proxy-match rate (Wilson
95% CI [0.5793, 0.8584]), while the full packet contains 40 matches, 31 mismatches,
and 29 ambiguous cases with low agreement (Fleiss κ = 0.1836). The second is a
blind reviewer-style packet that removes gold answers, EM/F1, baselines, and
these proxy judgments; four isolated adjudicators produce 53 match, 36 mismatch,
and 11 ambiguous judgments, with short-chain again weakest. Together, these
audits move the semantic-gap question from assertion to reproducible inspection:
structural states are useful audit metadata and routing causes, but not human
expert annotations or semantic correctness certificates.




6   Discussion


The experiments support a systems contribution: EvidenceFirst attaches
competitive saved answer artifacts to a pre-reader structural contract. It is
competitive on HotpotQA under saved protocols, the context-rich 2Wiki artifact
is strong under its saved reader-full condition, and the local-context stress row
exposes the boundary of that strength. The core contribution is the contract
itself: each reader call is tied to a checked, repaired, residual, or fallback graph
state that affects repair, fallback, selection, and replay before generation. The
boundary results define how this telemetry should be used: reader context and
answer selection dominate EM/F1, graph-only triage is modest, and 2Wiki gold-
chain audits show that structural states are not semantic proofs. For Web QA
operations, the concrete change is that answer logs become reproducible review
queues with typed causes: checked-path failures go to reader or selector inspection,
residual-gap cases go to graph repair, and fallback cases go to retrieval/context
review.

7    Threats to Validity

Protocol validity. The experiments use fixed benchmark contexts rather than live
Web search, and the HotpotQA and 2Wiki rows are not fully context-budget
isolated. We mitigate this by labeling rows as saved-protocol artifacts, reporting
the lower 2Wiki local-context stress boundary, and verifying every claim without
fresh generation.

Diagnostic validity. The checker is structural rather than semantic, depends on
lexical mapping and coarse answer-type filters, and only partially aligns with gold
2Wiki paths; the gold-chain, proxy, and blind reviewer-style audits are therefore
failure analysis, not professional human-level semantic validation.

Deployment validity. The 2Wiki comparison lacks a completed MS GraphRAG
run, fallback is barely exercised in final artifacts, ablations are partly compound,
and the selector row is deterministic postprocessing. Future work should add
professional manual gap-label adjudication, strict matched-budget reruns, fallback
stress tests, and semantic repair success analysis.


8    Conclusion

We presented EvidenceFirst, a KG-RAG pipeline that records structural
candidate-path state before generation. The method shifts the reliability object
from only the generated answer string to the retrieved evidence graph, exposing
missing entities, disconnected pairs, repair attempts, fallback cases, and selec-
tion state as reviewer-recomputable audit metadata. Across HotpotQA-1000
and 2WikiMultiHopQA-500, EvidenceFirst pairs competitive saved-protocol
accuracy with a pre-reader evidence-state trace. This turns fixed-context Web
QA runs into reproducible evidence-state transitions that operators can replay,
triage, and debug after deployment.
