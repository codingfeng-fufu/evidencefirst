      Abstract. Fixed-context Web Knowledge-RAG combines pages, entity-
      relation graphs, and LLM readers, but deployed systems still lack a
      reliable pre-generation answer to a basic operational question: is the
      Web evidence graph ready for the reader, or should the case be repaired,
      routed, or reviewed first? EvidenceFirst introduces an evidence-state
      control layer for Web Knowledge-RAG. Before generation, a determin-
      istic structural checker assigns each question to a structurally checked
      candidate path, repaired path, residual gap, or passage-fallback state;
      the state then controls localized graph repair, passage fallback, evidence
      routing, and later replay. The contract complements semantic answer
      checking by turning retrieved graph evidence into executable state before
      the reader output is finalized. The answer-quality rows place this control
      layer in a practical operating range: EvidenceFirst reaches 55.0/64.8
      on the HotpotQA end-to-end row, 56.2/65.6 on its selector sensitivity
      row, 69.0/75.8 in the context-rich 2Wiki reader-full audit setting, and
      50.4/59.5 under the stricter 2Wiki local-context stress boundary. The
      central empirical finding is operational: saved states create recomputable
      Web audit queues and a 2Wiki evidence-visibility audit without new LLM
      calls.

      Evidence-State Control · Web Question Answering


1   Introduction
Knowledge-intensive Web applications increasingly answer questions from a
mixture of retrieved pages, extracted entities, and knowledge-graph structure.
In an enterprise search or public Web QA service, however, the operational
failure is not only that an answer may be wrong. The operator also needs to
know whether the evidence graph connected the entities required by the question,
whether a missing bridge was repaired, whether generation fell back to passages,
and whether the same decision can be replayed later for audit. RAG grounds
language-model answers in retrieved text [6], while KG-RAG and GraphRAG
systems add entity-relation structure over retrieved corpora [2–4]. For Knowledge
and RAG on the Web, graph construction, entity-relation evidence, multi-hop
answering, and operational audit meet in the same question: what state was the
Web evidence graph in before generation?

    The missing systems abstraction is an evidence-state contract between Web
knowledge retrieval and answer generation. A GraphRAG pipeline can retrieve
relevant triples while still missing the bridge edge that makes the answer derivable.
It can retrieve both endpoint entities but leave them in disconnected components.
It can also retrieve a plausible graph neighborhood that lacks the actual candidate
support chain. In all of these cases, a retrieve-then-generate pipeline may still
produce a fluent answer, but after generation the log cannot tell whether the
failure belongs to retrieval, graph construction, graph repair, reader behavior, or
answer selection.
    EvidenceFirst turns the evidence graph into a control surface before the
reader is called. Instead of treating the generated answer string as the first
object to inspect, EvidenceFirst checks whether the constructed Web evidence
graph contains a structurally connected candidate chain for the question. The
checker assigns the case to a structurally checked candidate path, repaired path,
residual graph gap, or passage-fallback state. That state is executable rather
than merely logged: it is computed before the reader, determines graph repair
or passage fallback, constrains which evidence is passed to generation, records
the downstream selection decision, and can be replayed from saved artifacts. The
method therefore makes a focused systems claim: structural graph state is an
effective pre-reader interface for routing and auditing Knowledge-RAG failures
on fixed Web evidence. The path/gap state gives the system a control boundary
before answer generation, where repair and fallback decisions can be made from
the graph condition rather than from the final answer string.
    Table 1 makes the Web information-system requirements explicit. The key
difference from passive traces is that EvidenceFirst records the evidence
condition that controlled generation, not merely an explanation after an answer
has already been produced. A checked-path failure can be routed to reader or
selector inspection; a residual gap can be routed to graph repair; an empty or
fallback state can be routed to retrieval and context review. Because the same
fields are stored in per-example artifacts, auditors can replay the state transitions
without fresh LLM calls.

    The paper studies this Web Knowledge-RAG problem in fixed-context Web-
style evidence corpora. HotpotQA and 2Wiki provide retrieved passages, en-
tity mentions, and linked evidence graphs; EvidenceFirst focuses on how a
Knowledge-RAG system exposes and uses the retrieved graph state before genera-
tion. The reported accuracy rows place the control layer within a usable Web QA
range: under recorded protocols, EvidenceFirst preserves usable answer quality
while adding state telemetry that standard baselines do not expose. The paper’s
core evidence is operational: saved states create audit queues whose top-20% risk

graph states add typed causes for repair or reader inspection. Support-visibility,
local-context, gold-chain, and proxy/blind audits then show where fixed-context
graph state is strongest as a control signal.

Contributions. This paper makes three contributions:
 – We formulate a Web Knowledge-RAG evidence-state contract: every answer
   is tied to a structurally checked, repaired, residual, or fallback graph state
   computed before generation and replayable after deployment.
 – We implement this contract as structural control logic, where gap states drive
   localized graph repair, passage fallback, evidence routing, answer-selection
   audit, and typed Web audit queues.
 – We show that the control layer can preserve usable answer quality while pro-
   ducing replayable Web audit queues, validated with HotpotQA and 2Wiki ar-
   tifacts, paired statistics, operational removals, risk stratification, proxy/blind
   inspections, and no-LLM claim verification.


2   Related Work
RAG, GraphRAG, and multi-hop retrieval. RAG conditions a language model
on retrieved evidence [6], while GraphRAG systems organize retrieved infor-
mation into entity, relation, or community structures [2–4]. IRCoT interleaves
retrieval with chain-of-thought reasoning [10], A-RAG uses an agentic retrieval
trajectory [1], and HopRAG performs logic-aware graph retrieval and pruning [8].
These systems use graphs primarily to acquire, traverse, or compress evidence
for a reader. EvidenceFirst targets a different stage of the same Web KG-
RAG pipeline: after graph evidence has been retrieved or constructed, it records
whether that graph is in a checked, repaired, residual, or fallback state before
the reader is called.

Knowledge graphs for Web information systems. Web knowledge graphs expose
entity and relation structure for search, question answering, and information
fusion, but their operational value depends on how graph state is exposed to
downstream components. A retrieved subgraph may contain useful Web evidence
while still omitting a bridge entity, separating endpoint entities into different
components, or exposing only a shallow relation that is insufficient for a multi-hop
query. EvidenceFirst treats these cases as first-class Web information-system
4       Anonymous

states. Rather than adding another retrieval score, it records the graph condition
that the reader actually saw and turns that condition into a repair, fallback, or
audit route.

Verification and auditability. S2G-RAG judges whether evidence memory is
sufficient and emits text gap items [7], while RAGChecker defines diagnostic
metrics for retrieval and generation modules [9]. EvidenceFirst narrows the
claim to a different object of control: a per-question graph state whose path/gap
label is stored before generation, affects repair and fallback routing, records
selection state, and can be recomputed from saved artifacts. The distinction
is the timing and control boundary. RAGChecker-style metrics score modules
after outputs are available, and sufficiency-style systems emit gap judgments
over evidence; EvidenceFirst stores a graph state before the reader output is
finalized and uses that state to select the repair or fallback route whose result is
later replayed.


3     Method

3.1   Web Knowledge-RAG Problem Setting

We model a Web Knowledge-RAG query as a fixed-context inference problem
over retrieved or provided Web evidence. Given a question q, candidate passages
P = {pi }, and a per-question evidence graph G = (V, E) built from the same
visible evidence, the system must output a short answer a and a diagnostic record
D. Nodes in G are entities or evidence units, and edges are extracted relations,
support links, or passage-level associations. The setting covers search results,
Wikipedia-style pages, entity descriptions, and linked Web documents; it does
not assume live crawling or changing Web content during inference.
    The central object of control is the pre-reader evidence state of G. Standard
RAG readers consume passages directly, and many GraphRAG systems use graphs
to retrieve or compress context for the reader. EvidenceFirst instead asks
whether the visible graph contains a connected candidate chain before the reader
is called. Bridge questions require an intermediate entity or relation; comparison
questions require compared attributes or entities before the reader decides the
answer. This structural view is designed for routing: using only test-time graph
and passage evidence, it exposes whether the retrieved Web knowledge graph is
connected enough to justify a reader attempt.
    Operationally, EvidenceFirst records a structural path-state contract before
generation. For each question, the graph state is recorded as one of four states: a
checked structurally connected candidate path found in the retrieved evidence
graph, a repaired path after localized graph expansion, a residual graph gap after
unsuccessful repair, or a passage-fallback state when usable graph evidence is
absent. The diagnostic record D stores path-checked status, path length, gap
type, missing-entity and disconnected-pair counts, repair and fallback step tags,
and the final answer-selection flag. This contract is the method’s main difference

Algorithmic contract. Given question q, visible passages P, and evidence graph
G, EvidenceFirst executes a fixed state machine before the final reader output.
It first retrieves question triples and local passages, extracts question entities
with named-entity and proper-noun fallbacks, filters generic terms, normalizes
strings, and maps entities to graph nodes by exact, substring, and token-overlap
matching with threshold 0.85. It then selects non-question candidate nodes, filters
them by a coarse answer type inferred from q, and tests shortest paths in the
evidence subgraph. Non-yes/no questions require at least a two-edge support
path; yes/no questions require at least one edge. If an adequate path exists, the
state is checked and the extracted chain is sent to the reader. Otherwise, the
checker emits missing_entity, disconnected, bridge, or short_chain; empty
graph evidence becomes passage fallback. Missing entities trigger A+ expansion,
disconnected pairs trigger B bridge extraction over at most five endpoint pairs,
and every repair is followed by the same structural recheck. A complete recheck
becomes a repaired path; otherwise the residual gap or fallback state is retained
through generation and selection. The invariants are that the state is written
before the reader call, each state has a control action, and the saved fields can be
replayed from the graph, repair log, and selector decision without new generation.
These rules are fixed before evaluation and use no gold answers or support facts
at test time.

3.2     Evidence-First Inference
EvidenceFirst performs inference by applying the state machine in Figure 1.
It builds or loads a per-question KG, retrieves triples and passages, applies the
pre-reader structural check, optionally repairs and rechecks localized gaps, and
generates from the evidence packet selected by the resulting state. Empty graph
evidence routes to passages instead of being silently treated as complete, and
residual gaps remain attached to the final answer record.

that relevant endpoint entities are present but lie in separate components. A
bridge gap means that a partial path reaches one side of the answer entity but
lacks the relation needed to connect the reasoning chain. A short chain means
that a connection exists but is too shallow for the inferred question type. Empty
evidence means that KG retrieval returned no usable support and the reader
must fall back to passages.
    Representative saved 2Wiki records show why graph readiness and answer
correctness should be inspected separately. A correct answer can carry a missing-
entity graph label, while a structurally connected candidate path can mismatch
a posthoc gold-chain proxy. These divergences motivate audit/control states over
the saved graph.
    Diagnostic repair is localized to the reported gap. For missing entities, Evi-
denceFirst extracts triples about the missing entity from the retrieved passages
and adds them to the evidence graph. For disconnected pairs, EvidenceFirst
processes at most five entity pairs and extracts bridging triples from the same
passage context. After each repair stage, the structural checker is run again
and the new chain length, gap type, and repair statistics are appended to D.
When the graph remains incomplete, the reader still receives the available triples
together with local passages, while D records the residual gap. This design avoids
presenting a repaired answer as if the graph had been complete from the start.
Repair uses only the candidate passage and graph context available to the system;
it does not use gold answers or gold support facts at test time. The structural
check and saved-state replay are deterministic functions of the saved triples and
logs; graph repair itself may use the same temperature-zero LLM extraction
backend as KG construction, so replayability is defined over saved artifacts.

3.4   Grounded Reading, Selection, and Canonicalization
The answer reader receives the selected evidence triples and local passages
associated with the current evidence route. The reader is instructed to produce
a concise answer rather than a long explanation. A final selection step decides
whether to use the evidence-grounded postprocessed answer, and a lightweight
canonicalizer normalizes title casing, entity aliases, yes/no outputs, and short
answer forms when supported by the available context.
    This stage is intentionally downstream of structural path-state checking.
Reader context can compensate for imperfect graph evidence, but the saved route
remains attached to the output. As a result, EvidenceFirst can distinguish
cases where the graph was structurally complete but the reader failed from
cases where generation was attempted after repair or fallback. Local passage
context is enabled in the main EvidenceFirst setting and disabled only in the
reader-context ablation, so the ablation isolates how much answer realization
depends on text grounding beyond graph triples.
    The selector is conservative. It accepts the refined answer when the original
answer is malformed, when the refined answer is normalization-equivalent to the
original answer, when the refined answer is a shorter supported form, or when
it repairs a question-type mismatch such as a yes/no placeholder for an entity
question. Otherwise, the KG-grounded answer is preserved. The diagnostic record
therefore includes not only graph states, but also whether the final answer was
selected from the refined evidence-grounded path.


4     Experimental Setup
Datasets. We evaluate on two multi-hop QA settings. HotpotQA-1000 is a
1000-question distractor-style evaluation set with repaired contexts from the
HotpotQA validation split [11]. 2WikiMultiHopQA-500 is a 500-question sample
from 2WikiMultiHopQA [5]; each example contains natural-language passages
and Wikidata-derived evidence triples, entity ids, evidence ids, and answer
ids. The 2Wiki sample contains 5000 question-context pairs and 3346 unique
passage bodies for graph-based baselines. During inference, EvidenceFirst uses
the question, candidate passages, and constructed graph fields only; support
annotations, evidence ids, answer ids, and gold answers are loaded only after
prediction for offline diagnostics.
    Both benchmarks combine Web-style text with linked entities and require
multi-hop evidence composition; 2Wiki additionally exposes Wikidata-derived
support identifiers for offline diagnostics. They instantiate a fixed-context Web
QA setting rather than live Web search, so the experiments test evidence-state
control over available passages and graph evidence, not crawling, freshness, or
changing page content.

Evaluation questions. The evaluation is organized around four Web Knowledge-
RAG questions. First, can a pre-reader graph-state contract be attached to
answer artifacts while preserving usable answer quality? Second, do the saved
8       Anonymous

states create replayable audit queues without rerunning generation? Third, do
graph-state labels provide useful routing causes as structural audit labels? Fourth,
how sensitive are the answer results and evidence visibility to reader context and
postprocessing under explicit protocol boundaries?

Baselines. On HotpotQA-1000, we compare with Naive RAG, IRCoT [10],
A-RAG [1], LightRAG [3], MS GraphRAG [2], and HopRAG strict [8]. On
2WikiMultiHopQA-500, the completed baselines are Naive RAG, IRCoT, A-
RAG, LightRAG, and HopRAG strict. Main tables include completed full-sample
artifacts with independent strict rescoring. For HotpotQA, paired claims use
the strict response-only HopRAG row; the artifact bundle also keeps the legacy
HopRAG extraction file (0.5470 EM / 0.6498 F1) for reproducibility.

row. A separate 2Wiki visibility audit measures how much annotated support

Metrics and reporting boundary. We use exact match (EM) and token F1 with

deterministic selector sensitivity row over saved artifacts with no fresh LLM calls;

shared question IDs, bootstrap CIs, exact McNemar tests for EM, and explicit
labels for exploratory subgroup rows or compound ablation switches. The 2Wiki
visibility audit uses support-title recall and gold evidence-entity coverage only
after prediction; it does not supply support facts, evidence ids, or gold answers
to inference.

Implementation settings. The reported runs use the repository’s OpenAI-style
backend with qwen-plus on a DashScope-compatible endpoint unless a run
script explicitly overrides it. Answering and repair calls use temperature 0;
KG construction artifacts are cached and loaded for the reported evaluations.
The main pipeline uses max-iter 3, local passage top-k = 5, and at most five

Artifacts and reproducibility boundary. Every reported result is computed from

porting is artifact-limited and averaged per example: EvidenceFirst uses 5.711

5.938 calls and 6540.4 tokens on 2Wiki.


5     Results

5.1   Answer-Quality Envelope Under Recorded Protocols

Table 4 reports EM/F1 for the recorded protocols of the state-control layer.
The end-to-end saved EvidenceFirst run reaches 55.0% EM and 64.8% F1 on
HotpotQA-1000, and the deterministic selector sensitivity row reaches 56.2%
EM and 65.6% F1. These rows show that the control layer operates at strong-
baseline answer quality. The paired full-set intervals in Table 5 cross zero, so these
HotpotQA rows establish the operating range for the control layer; the systems
claim rests on the added state trace and routing utility. The bridge subset has
the largest observed paired gain and is reported as exploratory evidence.
    The same table reports two 2WikiMultiHopQA-500 protocol rows. The reader-
full audit row evaluates the context-rich audit setting and reaches 69.0% EM /
75.8% F1; the local-context stress row reaches 50.4% EM / 59.5% F1 and marks
the stricter context boundary. The visibility audit in Table 10 quantifies the
evidence boundary: reader-full keeps all annotated support titles visible, while
local top-k retrieval traces and A-RAG read chunks expose substantially less
annotated support.

5.3      Operational Removals

Table 7 reports four operational removals on both datasets. Two switches are
intentionally compound: disabling structural checking also disables gap-driven
repair, and disabling reader context also disables passage-based answer refine-
ment. The largest answer-quality drop comes from removing reader-context and
refinement, which reduces HotpotQA EM from 0.5620 to 0.2360 and 2Wiki EM
from 0.6900 to 0.1840. This result shows that graph triples alone do not provide
enough surface evidence for robust answer realization. Removing graph repair
reduces 2Wiki EM by 4.0 points and HotpotQA EM by 0.8 points, while remov-
ing answer refinement hurts HotpotQA but increases 2Wiki F1. These mixed
answer-level effects clarify the paper’s scope: structural checking and repair add
observability and routing controls, and the answer-quality changes show how
those controls interact with the reader under each recorded protocol.
    The checker ablation tests loss of control-state observability. When chain-

5.4      Diagnostic Validity and Failure Analysis
The saved audit records expose structural states before answer scoring. On
HotpotQA, 56.8% of examples end with a checked candidate path, repair is
attempted on 63.7%, and 43.49% of attempted repairs end with a structurally
connected recheck; on 2Wiki, the corresponding rates are 47.8%, 60.0%, and
22.0%. These are structural recheck-complete rates. Internal label-consistency
checks over saved fields show that missing-entity, disconnected, and short-chain
labels satisfy their structural invariants on both datasets; the HotpotQA checked-
path label is 98.44% consistent because nine incomplete rows carry an empty final
gap label. Thus, the method records whether an answer came from checked-path,
repaired, or residual incomplete evidence before answer scoring.
     Answer selection is informative but not sufficient: selected answers reach
0.6273 EM versus 0.2626 EM for non-selected answers on HotpotQA, and 0.7358
versus 0.5811 EM on 2Wiki. Table 8 therefore separates triage signals and reports
lift over the base error rate. The composite audit-risk score combines answer

alone, while the graph-only score is modest; this supports review prioritization
with structural failure causes.

6    Discussion
The experiments support three systems claims for Knowledge Graphs and RAG
on the Web. First, EvidenceFirst attaches a pre-reader control contract to
answer artifacts and retains usable answer quality under the recorded protocols.
Second, each reader call is tied to a checked, repaired, residual, or fallback graph
state that affected repair, fallback, selection, and replay before generation. Third,
evidence states are most useful as routing and audit objects: reader context and
answer selection dominate EM/F1, while graph state contributes typed causes
for reader inspection, graph repair, or retrieval/context review.


7    Threats to Validity
Protocol validity. The experiments define a fixed-context Web Knowledge-RAG
setting with recorded, but not uniform, context budgets. The supported claim
is fixed-context graph-state control: every reported row has a saved evidence
condition, the 2Wiki table separates reader-full and local-context rows, and the
verifier recomputes the main claims without fresh generation.

Diagnostic validity. The checker is structural rather than semantic, depends on
lexical mapping and coarse answer-type filters, and only partially aligns with
gold 2Wiki paths. The gold-chain, proxy, and blind audits calibrate the saved
states as routing metadata while keeping semantic evidence validation separate.

Deployment validity. The artifact boundary has practical consequences: 2Wiki
lacks a completed MS GraphRAG run, passage fallback is rare in the saved rows,
ablations are partly compound, and the selector row is deterministic postprocess-
ing. Future work should add professional gap-label adjudication, fallback stress
tests, semantic repair-success analysis, and deployment-scale uniform-budget
Web retrieval runs.


8    Conclusion
We presented EvidenceFirst, a Web Knowledge-RAG pipeline that records
structural candidate-path state before generation. By shifting reliability logging
from only the answer string to the retrieved evidence graph, EvidenceFirst
exposes missing entities, disconnected pairs, repair attempts, fallback cases, and
selection state as recomputable audit metadata. The result is a fixed-context
Web Knowledge-RAG run that operators can replay, triage, and debug after
deployment.
